# UptimeWatch — дизайн

Дата: 2026-10-30
Статус: черновик спецификации, ожидает проверки автором

## Цель

Портфолио-проект .NET-разработчика уровня middle: сервис мониторинга доступности сайтов (аналог UptimeRobot).
Работодатель за 5–10 минут должен увидеть живое демо, прочитать README и найти в коде осмысленную архитектуру, тесты, Docker и CI.

## Допущения

- Проект сольный, разрабатывается на .NET 9 (SDK 9.0 установлен).
- Запуск локально через Docker Compose; публичный деплой — отдельный шаг после готовой версии.

## Объём первой версии

**Входит:**
- Добавление мониторов (URL, интервал, ожидаемый код ответа).
- HTTP-проверки в фоне, история результатов, аптайм за 24 часа, 7 и 30 дней.
- Инциденты: открытие и закрытие, длительность простоя.
- Живой дашборд (SignalR) без перезагрузки страницы.
- Алерты в Telegram при падении и восстановлении.
- Пользователи: регистрация, вход, у каждого свои мониторы.

**Не входит:** публичная статус-страница, графики, проверка срока SSL, TCP/ping-проверки, повторная отправка алертов, подтверждение email.

## Архитектура

Модульный монолит, слои по Clean Architecture. Одно приложение ASP.NET Core: Blazor Server, фоновый сервис проверок и SignalR-хаб.

```
UptimeWatch/
├─ src/
│  ├─ UptimeWatch.Domain          — сущности и правила, без зависимостей
│  ├─ UptimeWatch.Application     — сценарии использования, интерфейсы
│  ├─ UptimeWatch.Infrastructure  — EF Core, HTTP-проверки, Telegram
│  └─ UptimeWatch.Web             — Blazor Server, SignalR, Identity, фоновый сервис
├─ tests/
│  ├─ UptimeWatch.Domain.Tests
│  ├─ UptimeWatch.Application.Tests
│  └─ UptimeWatch.Integration.Tests   — Testcontainers + PostgreSQL
├─ docker-compose.yml
└─ .github/workflows/ci.yml
```

Зависимости направлены внутрь: `Web → Application ← Infrastructure`; `Domain` ни от кого не зависит.

### Сущности

- `Monitor`: URL, интервал, ожидаемый код ответа, владелец, статус, `NextCheckAt`.
- `CheckResult`: время, успех, код ответа, время ответа (мс).
- `Incident`: начало и конец простоя.
- Пользователь: ASP.NET Core Identity; у монитора есть `OwnerId`.

### Интерфейсы в Application

- `IHealthChecker` — выполняет одну проверку. Эта граница позволяет позже вынести проверки в отдельный Worker.
- `INotifier` — отправка алертов (Telegram сейчас, другие каналы потом).
- `IMonitorNotifications` — оповещение дашборда о новых результатах через SignalR.

Бизнес-правила (когда сайт считается упавшим, когда открывать и закрывать инцидент) живут в `Domain` и тестируются без БД и сети.

## Поток данных

1. Фоновый сервис `MonitorScheduler` раз в несколько секунд выбирает включённые мониторы с `NextCheckAt <= now`.
2. Для каждого вызывается `IHealthChecker.CheckAsync`. Проверки идут параллельно с ограничением (например, 20 одновременно, `SemaphoreSlim`).
3. `HealthChecker` делает запрос через `HttpClient` из `IHttpClientFactory` с таймаутом, замеряет время ответа и сравнивает код с ожидаемым. Любое исключение (DNS, таймаут, SSL) превращается в неуспешный `CheckResult`, а не в падение сервиса.
4. Результат сохраняется в БД, затем `NextCheckAt = now + interval`.

### Инциденты

- Монитор считается упавшим после **3 подряд неудачных проверок** (порог настраивается) — защита от ложных срабатываний.
- В этот момент открывается `Incident` и вызывается `INotifier`: «сайт упал».
- Первая успешная проверка закрывает инцидент; приходит уведомление «восстановлен» с длительностью простоя.
- Пока инцидент открыт, повторных алертов нет.

### Живой дашборд

После сохранения результата событие уходит через SignalR в группу владельца монитора. Blazor-компонент обновляет карточку без перезагрузки. Пользователь видит только свои мониторы.

### Аптайм и история

Аптайм считается запросом по `CheckResult`. Фоновая задача удаляет результаты старше 30 дней.

### Отказоустойчивость

- Состояние (`NextCheckAt`, открытые инциденты) хранится в БД, поэтому перезапуск ничего не теряет.
- Недоступность Telegram логируется и не ломает цикл проверок.

## Пользователи и безопасность

- ASP.NET Core Identity в той же PostgreSQL; регистрация по email и паролю.
- Все запросы в `Application` фильтруются по владельцу: чужой монитор нельзя открыть, подставив его id.
- Telegram: пользователь вводит свой `chat_id` в профиле и получает тестовое сообщение. Токен бота один на приложение, хранится в user-secrets локально и в переменной окружения в Docker, не в репозитории.

### Защита от SSRF

Приложение ходит по URL, которые вводит пользователь, поэтому:
- разрешены только `http` и `https`;
- запрещены loopback, приватные сети и link-local адреса (проверка после DNS-резолва);
- лимит мониторов на пользователя и минимальный интервал (например, 30 секунд);
- ограничены таймаут и размер читаемого ответа.

## Тестирование

- `Domain.Tests` (xUnit): правила инцидентов, порог неудач, валидация URL.
- `Application.Tests`: сценарии с заглушками `IHealthChecker` и `INotifier`.
- `Integration.Tests` (Testcontainers + PostgreSQL): репозитории, фильтрация по владельцу, полный цикл «проверка → инцидент → уведомление» против тестового HTTP-сервера.
- GitHub Actions запускает сборку и тесты при каждом пуше.

## Поставка

- `docker compose up` поднимает приложение и PostgreSQL; миграции применяются при старте.

- Деплой на бесплатный хостинг — отдельный шаг после готовой версии.
